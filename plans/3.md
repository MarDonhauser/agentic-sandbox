# Plan for #3: Add DELETE /api/runs/:id

## Goal
Test engineers can remove a run recorded against the wrong vehicle:
`DELETE /api/runs/:id` removes it (204) unless it is unknown (404) or in status
`running` (409). Listing, creating, reading, the page and the env contract stay.

## Files to change (confirmed / plausible / open)
- **confirmed** `src/runs.ts` — `RunStore` (line 49) has `list`, `get`, `create`
  but no removal. The "a run in progress must not be deleted" rule is domain
  logic, so it belongs here, not in the route (`.github/instructions/src.instructions.md`
  line 7). Add `remove(id): "deleted" | "not-found" | "in-progress"`.
- **confirmed** `src/app.ts` — routes live here; add `app.delete("/api/runs/:id")`
  next to `GET /api/runs/:id` (line 30), mapping the three outcomes to 204/404/409.
  The 404 shape copies line 32: `{ error: "run not found", id }`.
- **confirmed** `test/app.test.ts` — `.github/instructions/src.instructions.md`
  line 9 requires a supertest unit test for every new endpoint.
- **confirmed not affected** `public/index.html` (line 42 renders a read-only
  table; the ticket asks for no delete control), `e2e/smoke.spec.ts`, `k8s/*`,
  `README.md` (it documents env vars, not endpoints), `src/config.ts`.
- **open** whether the 409 body should carry the `id` as the 404 body does. The
  ticket fixes only `error: "run is in progress"`. I add `id` for symmetry with
  line 32 and list it as an assumption in the PR.

## Tests
`test/app.test.ts`, three cases in the existing `runs api` describe:
1. delete a seeded run -> 204, body empty, `GET /api/runs` one shorter, `GET /api/runs/<id>` 404
2. `DELETE /api/runs/run-9999` -> 404 `{ error: "run not found", id }`
3. delete a run in status `running` -> 409 `{ error: "run is in progress" }`, run still listed

**How case 3 reaches status `running`.** No code path in this repository ever
produces it: `RunStore.create` hardcodes `status: "planned"` (`src/runs.ts` line
71) and no route writes the status (`src/app.ts` has GET, GET/:id, POST only).
The endpoint that would is ticket #6 (`docs/tickets/06-run-status-transitions.md`
line 4: "Today the status is always `planned`"), which is out of scope here. The
test therefore sets the status on the stored object directly
(`store.list()[0].status = "running"`) using a local `buildAppWithStore()` helper.
That is honest about the gap: the guard is covered, but only at unit level and
only through the store, never through HTTP. I do not add a status-setting method
or endpoint to make the test prettier, and I do not weaken the assertion to
something reachable today. Once #6 exists, this case should be rewritten to
PATCH the run to `running` first. Stated in the PR and in the issue comment.

## Environment contract
Untouched. No variable is added to `src/config.ts`, so `k8s/configmap.yaml` and
the README table stay as they are.

## Risks
- Unit: a deletion leaking between tests would break the existing "lists seeded
  runs" assertion. Each test builds its own app and store, so it cannot.
- Rollout / stability / smoke: unaffected, no config or manifest change.
- Browser: `e2e/smoke.spec.ts` counts table rows; the page is not changed, so the
  pipeline's browser step should be unaffected.
- `express.static` (`src/app.ts` line 19) only serves GET/HEAD, so it cannot
  swallow the DELETE.

## Open questions
Neither blocks implementation (`plan-ticket` step 7), so work continues.
1. Should the 409 body carry `id` and the current `status`? Going with `id` only.
2. Should the ticket text state that `running` is unreachable until #6? Yes, in my view.
