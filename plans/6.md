# Plan for #6: Add PATCH /api/runs/:id/status with allowed transitions

## Goal
A client can move a run forward through its lifecycle: `PATCH /api/runs/:id/status`
with `{ "status": "running" }` sets the new status and returns the updated run.
Only `planned -> running` and `running -> done` are allowed; every other pair is
refused with 409, an unknown id with 404. Creating, listing, and reading runs stays
exactly as it is; the web page is not touched.

## Tests

  updated run, and the change is visible in a following `GET /api/runs/:id`),
  invalid transition `planned -> done` (409, `error: "invalid transition"`, `from`,
  `to`), unknown id (404, `{ error: "run not found", id }`), and an unknown status
  value in the body (400 with `details`, see risk 2).

## Environment contract

## Risks
1. Order of checks: the ticket wants 404 for an unknown id and 409 for a bad
   transition. The route resolves the run first, so an unknown id answers 404 even
   when the body is also wrong.
2. The ticket says "anything else answers 409". A body like `{ "status": "banana" }`
   is not a transition at all but a malformed request. Decision: unknown or missing
   status values are a `ValidationError` -> 400 with `details`, per the error rule in
   `AGENTS.md:42`; 409 is reserved for a well-formed but forbidden transition
   (including `planned -> planned`). Documented in the PR.
3. Pipeline: only the `test` job is really affected. Rollout, stability, smoke and
   the browser check touch nothing this change alters (no config, no manifest, no
   page), so a red deploy job would point at the environment, not at this diff.

## Open questions
1. Should a repeated `PATCH` with the current status (`running -> running`) be an
   idempotent 200 instead of 409? Implemented as 409, because the ticket allows
   exactly two pairs. Non-blocking.
