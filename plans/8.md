# Plan for #8: Log every request as one JSON line with a request id

## Goal
Every HTTP request served by the Express app answers with an `x-request-id` header and
produces exactly one JSON log line when the response is finished, carrying id, method,
path, status and duration. Response bodies, routes, validation and the API contract do
not change; request bodies are still never logged.

## Files to change (confirmed / plausible / open)
- confirmed `src/app.ts` — `createApp` builds the middleware chain (line 16-19). The
  request-id middleware must run before `express.json()` and `express.static()` so that
  static and error responses are covered too.
- confirmed `src/log.ts` (new) — `src/server.ts:6` already has a private `log(level, msg, extra)`
  helper that writes `{level, msg, ts, ...extra}`. `src/app.ts` cannot import `src/server.ts`
  (it starts the listener and calls `process.exit`), so the helper moves into its own module
  and both files import it. One log format for the whole process.
- confirmed `src/server.ts` — drops the local helper, imports it from `./log.js`. No output change.
- confirmed `test/app.test.ts` — new `describe("request logging")` (supertest, per tests instructions).
- not affected: `src/config.ts`, `src/runs.ts`, `k8s/**`, `public/index.html`, `e2e/**`, `README.md`
  (no new endpoint, no new environment variable, no UI change).

## Tests
- `test/app.test.ts`: response carries an `x-request-id` header; a client-provided
  `x-request-id` is echoed unchanged; one log line per request with exactly the fields
  `level, msg, ts, id, method, path, status, durationMs` and `msg: "request"`; the POST body
  values do not appear in the log line.

## Environment contract
No variable added or required. `src/config.ts` is untouched, so `k8s/configmap.yaml` and the
README table stay as they are. `LOG_LEVEL` is loaded and validated but not used by any logging
code today; this change keeps that as it is instead of silently introducing level filtering.

## Risks
- unit: the log assertion reads `console.log` through a spy; if the `finish` event fired after
  supertest resolved the test would be flaky. Verified locally.
- build/lint: `process.hrtime.bigint()` returns a bigint; the duration must be converted before
  it reaches `JSON.stringify`, which throws on bigint.
- rollout/stability/smoke/browser: unchanged startup path, no new variable, no route change, so
  the pipeline risk is low. The browser test runs anyway because every page request now passes
  the new middleware.
- The ticket lists the log fields without `ts`. Reusing the existing helper adds `ts`; dropping it
  would give the process two different log formats. Extra fields are allowed by AGENTS.md
  ("one JSON object per line with `level` and `msg`"), so the helper wins.

## Open questions
None of these block the implementation; each is decided in the PR text.
1. `path`: logged as `req.path` (no query string), matching the field name in the ticket.
2. The metrics listener in `src/server.ts` is a raw `http` server, not Express; it stays unlogged.
3. An incoming `x-request-id` is echoed as sent (trimmed, non-empty), not validated as a UUID.
4. AGENTS.md "Map" lists the source files and will not mention the new `src/log.ts`.
