# Plan for #2: Reject CO2 values outside 0 to 500 g/km

## Goal
`POST /api/runs` must reject `co2GramsPerKm` values below 0 or above 500 with a 400 and a
`details` entry `"co2GramsPerKm must be between 0 and 500"`. Boundary values 0 and 500 stay
accepted. Nothing else about run creation, listing, or the schema changes.

## Dependencies (confirmed / plausible / open)
- **confirmed**, change: yes — `src/runs.ts` `validateNewRun()`: currently only checks
  `typeof co2GramsPerKm === "number" && !Number.isNaN(...)`; add a range check
  (0 <= x <= 500) appended to `details`.
- **confirmed**, change: yes — `test/app.test.ts`: add unit tests for below-range,
  above-range, and both boundary values (0 and 500 accepted).
- **confirmed**, change: no — `src/app.ts`: route already maps `ValidationError` to a 400
  with `details`; no route change needed since the error shape is unchanged.
- **plausible**, change: optional — `public/index.html`: the `#co2` input has no `min`/`max`
  attributes, so the browser lets users submit out-of-range values that the server will now
  reject with a generic-looking 400. Adding `min="0" max="500"` improves UX but is not
  required to satisfy the ticket's "done when" criteria (server-only). Verify: `grep` above
  showed no existing min/max on the input.
- **open**: none — this is a pure validation-logic ticket with no env var, no k8s manifest,
  and no route contract change.

## Tests
- `test/app.test.ts`: three new cases under `describe("runs api")`:
  - `co2GramsPerKm: -5` → 400 with `details` containing the exact range message.
  - `co2GramsPerKm: 9999` → same 400 message.
  - `co2GramsPerKm: 0` and `co2GramsPerKm: 500` → both `201 Created` (boundaries accepted).

## Environment contract
Not touched. No new/changed variables in `src/config.ts`, so no `k8s/configmap.yaml` or
README change needed.

## Risks
- Off-by-one on boundaries: must use `< 0` / `> 500`, not `<=`/`>=`, so 0 and 500 pass.
- Existing `SEED_RUNS` values (97.2–131.9) are all within range, so seeding still works.
- Pipeline: only unit tests affected; no rollout/deploy/browser risk since no route or schema
  shape changes. `npm run e2e` unaffected unless the optional HTML `min`/`max` attrs are added
  (still low risk, purely additive).

## Open questions
None — the ticket is fully specified (exact error message and boundary behavior given).

## Decisions
No open questions were raised; plan is ready to implement as written.
