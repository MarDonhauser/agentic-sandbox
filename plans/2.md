# Plan for #2: CO2 range validation

## Goal
Reject impossible CO2 emissions for measurement runs so `POST /api/runs` rejects values outside 0 to 500 g/km while allowing 0 and 500. This does not change the API shape or add new environment variables; it only tightens validation and tests.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed: `src/runs.ts` `validateNewRun` — add a numeric range check for `co2GramsPerKm` and emit `co2GramsPerKm must be between 0 and 500`; change: yes
- confirmed: `src/app.ts` `POST /api/runs` — passes validation errors through as HTTP 400 with `details`, so the new message is returned consistently; change: yes
- confirmed: `test/app.test.ts` — add unit coverage for below-range, above-range, and both boundary values; change: yes
- plausible: `public/index.html` form input — may need `min="0" max="500"` to match business rules in the browser, but the ticket only requires server validation; change: no (verify in browser)
- open: `README.md` / `k8s/*` — no env vars or deployment changes are implied by this ticket; change: no

## Tests
- `test/app.test.ts`: add a case for `co2GramsPerKm: -5` expecting 400 and the quoted detail
- `test/app.test.ts`: add a case for `co2GramsPerKm: 9999` expecting 400 and the quoted detail
- `test/app.test.ts`: add boundary acceptance checks for `0` and `500`

## Environment contract
- No new or required environment variables; `src/config.ts`, `k8s/configmap.yaml`, and the README table stay unchanged.

## Risks
- Clients that currently send out-of-range values will start failing with 400s and may need updated validation.
- A too-strict check could reject valid decimal values or the exact boundaries 0 and 500.
- Pipeline impact is low: the main risks are unit-test regressions or a browser regression if the UI form is later tightened without matching tests.

## Open questions
1. Should the UI also block invalid CO2 values in the browser form with `min="0" max="500"`, or is server-side validation enough?
2. Should the range error replace the generic numeric error only for out-of-range values, or should the existing "must be a number" message remain for NaN/invalid fields?

## Decisions
1. Browser validation: Server-side only.
2. Range error handling: Replace generic number message for out-of-range values.

The plan is ready to implement.
