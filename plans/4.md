# Plan for #4: Filter runs by vehicle on the web page

## Goal
A text input labelled "Filter by vehicle" above the runs table filters the visible rows
as the user types; clearing it shows every run again. The JSON API, the run store and the
add-run form stay exactly as they are.

## Files to change (confirmed / plausible / open)
- **confirmed** `public/index.html` — the only page. `load()` (line 39-43) writes the whole
  response into `tbody#runs`; there is no client-side state to filter over yet, so `load()`
  must keep the fetched runs and a `render()` must apply the filter.
- **confirmed** `e2e/filter.spec.ts` (new) — `e2e/smoke.spec.ts` is the only browser test today;
  a second spec file keeps the smoke test untouched.
- **confirmed, not changed** `src/app.ts:25-28` already supports `GET /api/runs?vehicleId=`,
  and `src/runs.ts:57-60` filters exactly. Client-side filtering is what the ticket asks for,
  so neither file is touched and `test/app.test.ts:41-46` keeps covering the server filter.
- **confirmed, not changed** `k8s/`, `src/config.ts`, `README.md` — no new variable, no new route.

## Tests
- `e2e/filter.spec.ts`: seeded page, type `WVW-1001`, assert 2 rows and that `WVW-2042` /
  `WVW-3310` are gone; clear the input, assert the full row count is back.
- `e2e/smoke.spec.ts` must still pass unchanged.
- No unit test changes: no server behaviour changes.

## Environment contract
No variable added or required. `src/config.ts`, `k8s/configmap.yaml` and the README table stay in sync.

## Risks
- **Locator collision (main risk).** `smoke.spec.ts:14` uses `getByPlaceholder("Vehicle ID")`
  and `:19` uses `getByRole("status")`, both non-exact and strict. A filter input whose
  placeholder contains "Vehicle ID", or a second `role="status"` result counter, makes those
  locators resolve to two elements and breaks the existing browser test. Therefore: the filter
  input gets a `<label>` and **no** placeholder, and no second status region is added.
- The pipeline runs `npx playwright test` (ci.yml:107) against the deployed pod, i.e. both spec
  files run against one shared in-memory store. The new test must not depend on the exact total
  row count while `smoke.spec.ts` may be adding a run in parallel — assert on the filtered set
  (`WVW-1001` = 2 seeded runs, a vehicle no other test uses) and on "more rows than filtered"
  after clearing, not on a fixed total.
- Pipeline steps that could fail: `browser` only. rollout/stability/smoke are untouched
  (no image, manifest or config change beyond a static file).

## Open questions
None that block. Two decisions taken and recorded here: filtering is case-insensitive substring
matching (so typing narrows progressively), and filtering happens client-side over the already
fetched runs, exactly as the ticket permits.
