# Plan for #4: Filter runs by vehicle on the web page

## Goal
Add a labelled vehicle filter above the runs table so users can type a vehicle ID and see matching rows update client-side, including restoring all rows when cleared. Keep the API, deployment, environment contract, and existing add-run behavior unchanged.

## Dependencies (confirmed / plausible / open), each with change: yes | no
- confirmed: `public/index.html` — `load()` currently renders all fetched runs directly into `tbody#runs`; add filter markup and client-side filtering. change: yes
- confirmed: `e2e/smoke.spec.ts` — existing Playwright tests use the page and role/placeholder locators; add the required `WVW-1001` filter assertion and preserve the add-run test. change: yes
- confirmed: `src/app.ts` — `GET /api/runs` already supports `vehicleId`, but the ticket permits client-side filtering; no route change is needed. change: no
- confirmed: `src/runs.ts` — seeded data contains two `WVW-1001` runs and other vehicles; no domain change is needed. change: no
- confirmed: `test/app.test.ts` — API filtering is already covered; no unit-test change is needed. change: no
- confirmed: `src/config.ts`, `k8s/configmap.yaml`, `README.md` — no new variable or API contract is required. change: no

## Tests
- `e2e/smoke.spec.ts`: type `WVW-1001` into the labelled filter and assert only matching rows are visible.
- `e2e/smoke.spec.ts`: retain the existing health and add-run browser tests; the filter test should also verify clearing restores all rows.

## Environment contract
No environment variable is added or changed. `src/config.ts`, `k8s/configmap.yaml`, and the README environment table remain unchanged.

## Risks
- Filtering the rendered rows instead of the source data could make clearing unreliable; retain the fetched run list separately.
- The filter must match the intended case behavior and not interfere with the add-run form.
- Playwright locator ambiguity or row-count timing could make the browser test flaky.
- Pipeline risks: browser check is directly affected; unit, rollout, stability, and smoke checks should remain unchanged.

## Open questions
1. None; the ticket explicitly allows client-side filtering and defines the label, behavior, and browser assertion.

## Decisions
- No open questions; the ticket permits client-side filtering and defines the required label and behavior.
