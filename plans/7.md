# Plan for #7: Add readiness and liveness probes, run two replicas

## Goal
The Deployment gets a readiness and a liveness probe on the health endpoint and runs two
replicas, so a rolling update never sends traffic to a pod that has not started yet.
Nothing changes for the API, the page, or the environment contract.

## Files to change (confirmed / plausible / open)
- **confirmed** `k8s/deployment.yaml` — `spec.replicas: 1` (line 7) and the container `app`
  have no `readinessProbe`/`livenessProbe`. Both additions go here.
- **confirmed** `src/app.ts` — serves the health endpoint (`app.get(...)`, line 21) on the
  container port from `src/config.ts` (`PORT`, default `3000`). Probe target.
- **confirmed** `k8s/service.yaml` — `targetPort: http`, the named port `http` = 3000 in
  `k8s/deployment.yaml`. Unchanged, but the probe must hit the same port.
- **plausible** `.github/workflows/ci.yml` — the stability step asserts every pod is ready
  and has no restarts; with two replicas it now checks two pods. Not edited (forbidden).
- **open** none.

## Tests
No unit or browser test changes. `k8s/` has no local test harness; the manifests are
verified only by the pipeline (rollout, stability, smoke, browser).

## Environment contract
No variable added or required. `src/config.ts` is untouched, so `k8s/configmap.yaml` and the
README table stay as they are.

## Risks
- rollout: if the probe path or port is wrong, the pods never become Ready and
  `kubectl rollout status --timeout=90s` fails.
- stability: an aggressive liveness probe restarts a healthy pod. Keep a conservative
  `initialDelaySeconds` / `periodSeconds`.
- scheduling: two replicas on the single-node kind cluster need 2x the requests
  (100m CPU, 128Mi). Small enough for a GitHub runner.
- smoke/browser: unaffected, the Service load-balances over both pods.
